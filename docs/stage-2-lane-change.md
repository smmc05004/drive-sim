# 2단계 — 차선 변경과 미러

> **검증 질문: 미러를 보고 차선 변경 타이밍을 잡을 수 있는가?**

## 목표

직선 도로에서 뒤차의 위치를 사이드미러로 확인하고, 안전한 시점에 차선을 변경한다.

이 단계에서 가르치려는 것은 조향 정밀도가 아니라 **판단과 타이밍**이다.

> "사이드미러에 뒤차가 어느 정도 크기·위치로 보일 때 들어가도 되는가"

## 산출물

- 다차선 직선 도로
- 룸미러 + 좌우 사이드미러
- 등속으로 직진하는 NPC 차량 몇 대
- 방향지시등
- 차선 변경 결과 피드백 (안전 / 위험 / 충돌)

## 미러 — 이 단계의 기술적 핵심

미러는 "그 장면을 또 다른 카메라로 다시 렌더링해서 거울 면에 붙이는" 방식이다. 씬을 3~4번 그리는 셈이라 비용이 있다.

### 방식 A — PiP 뷰포트 (먼저 이걸로)

`renderer.setScissor()` / `setViewport()`로 화면의 특정 영역에 씬을 다시 그린다.

- 룸미러, 좌 사이드미러, 우 사이드미러 각각 하나씩 → 총 4회 렌더
- 미러용 카메라는 **해상도, FOV, 렌더 거리를 줄인다.** 미러는 작게 표시되므로 품질을 낮춰도 티가 안 나고, 비용이 크게 준다
- 미러는 좌우 반전이므로 카메라 방향과 화면 뒤집기 처리 필요

PC 한정이라면 이 방식으로 충분하다.

### 방식 B — Render Target 평면 반사

미러 유리 평면에 render target 텍스처를 붙여 실제 평면 반사를 구현한다.

- **시차(parallax)가 실제와 맞는다.** 고개(카메라)를 움직이면 미러에 보이는 범위가 실제처럼 바뀐다
- "뒤차가 얼마나 뒤에 있나"의 학습 정확도가 A보다 높다
- 구현과 튜닝 비용이 더 크다

**A로 시작해서, 거리 판단 정확도가 부족하다고 느껴지면 B로 간다.** 이 판단은 실제로 플레이해봐야 알 수 있다.

### 미러 설계 시 주의

- **미러 각도와 시야각을 실제와 맞춘다.** 이게 틀리면 여기서 배운 감각이 실차에서 안 맞는다 — 이 게임의 존재 이유가 무너지는 종류의 오류다
- 사각지대(blind spot)를 실제와 같게 남긴다. **사각지대의 존재를 가르치는 것이 이 레슨의 핵심 중 하나**다
- 사이드미러는 볼록거울이라 실제보다 멀어 보인다. PoC에서는 평면으로 두되, 이 차이를 문서화하고 나중에 왜곡을 검토한다
- 좌핸들 기준 (한국)

## 도로

- 3차선 직선, 차선 폭 3.5m
- 차선 도색 (실선/점선 구분)
- 갓길, 중앙분리대
- 길이 2~3km. 끝에 도달하면 순환시켜 무한 도로처럼 처리

곡선 도로는 이 단계에서 필요 없다. 판단 학습에 집중한다.

## NPC 차량

**AI를 만들지 않는다.** 등속 직진만 한다.

- 각 차량은 지정된 차선에서 지정된 속도로 직진
- 속도 패턴을 시나리오 데이터로 정의 (내 차보다 빠른 차, 느린 차, 비슷한 차)
- 충돌 회피 로직 없음 — 사용자가 잘못 끼어들면 실제로 부딪힌다. 그래야 학습이 된다

시나리오 예시:

| 시나리오 | 구성 | 학습 목표 |
|---|---|---|
| 여유 있는 변경 | 뒤차가 훨씬 뒤 | 기본 절차 익히기 |
| 접근 중인 차 | 뒤차가 나보다 빠름 | 상대 속도 판단 |
| 사각지대 | 옆 차선 사각지대에 차 | 어깨 너머 확인의 필요성 |
| 연속 변경 | 1→2→3차선 | 절차 반복 |

## 차선 변경 절차와 판정

실제 교육에서 가르치는 순서를 그대로 채점 항목으로 삼는다.

1. 방향지시등 켜기
2. 룸미러 확인
3. 해당 방향 사이드미러 확인
4. (사각지대 확인 — 고개 돌리기)
5. 완만하게 조향
6. 차선 중앙 정렬 후 지시등 끄기

### 판정

| 결과 | 조건 |
|---|---|
| **안전** | 변경 완료 시점에 뒤차와의 간격이 충분 (상대속도 고려한 TTC 기준) |
| **위험** | 뒤차가 감속해야 할 정도로 가까움. TTC 임계값 이하 |
| **충돌** | 실제 접촉 |
| **절차 미흡** | 지시등 미사용, 미러 미확인 |

"미러 확인"을 어떻게 판정할지가 설계 과제다. PiP 방식에서는 시선 추적이 불가능하므로, **미러를 확대해서 보는 키(예: 좌/우 미러 확대)를 두고 그 사용 여부로 판정**하는 방식을 검토한다. 실제 고개 돌림을 대체하는 장치다.

### 사각지대 확인

키 하나로 좌/우로 시선을 돌린다(카메라 회전). 실제 어깨 너머 확인에 대응한다. 이 동작 중에는 전방이 안 보인다는 점까지 재현되어야 학습이 정직해진다.

## 피드백

- 결과를 시각적으로 즉시 표시 (안전/위험/충돌)
- 위험·충돌 시 **왜 위험했는지** 리플레이 또는 다이어그램으로 설명
- 절차 체크리스트 표시 (지시등 ✓, 룸미러 ✓, 사이드미러 ✗)

단순히 "실패"라고 하면 배우는 게 없다. 무엇이 부족했는지 보여줘야 한다.

# 구현 노트 (완료 후 기록)

## 1. Three.js `rotateY(π)` 는 오일러 각을 (0, π, 0) 으로 저장하지 않는다

이번 단계에서 가장 오래 잡아먹은 버그다.

0단계부터 운전석 카메라를 `driverCamera.rotateY(Math.PI)` 로 뒤집어 왔다.
2단계에서 고개 돌리기를 넣으면서 매 프레임 `rotation.y = Math.PI + lookYaw`
를 대입했더니 **운전석이 뒤를 보기 시작했다.**

원인: π 회전의 XYZ 오일러 분해는 유일하지 않다. Three 는 `(0, π, 0)` 이 아니라
**`(π, 0, π)`** 로 저장한다 (같은 회전, 다른 분해). 그래서 `rotation.y` 는 0 이었고,
거기에 π 를 대입하면 `(π, π, π)` 라는 전혀 다른 회전이 된다.

**증상이 사람을 헷갈리게 했다.**

- 실내(보닛·대시보드·핸들)가 통째로 사라졌다 — 전부 차체 앞쪽(+Z)에 있으니까
- 대신 뒷바퀴가 화면 아래에 크게 보였다 — 앞바퀴인 줄 알고 보닛 크기를 계속 키웠다
- `root.visible=true`, `children=5` 로 씬 그래프는 멀쩡했다
- 좌우가 뒤집혀 보여서 **1단계에서 고친 좌표 규칙이 틀린 줄 알았다**

`rotation.set(0, Math.PI, 0)` 으로 명시하니 한 번에 해결됐다.
**회전을 나중에 오일러로 수정할 계획이면 처음부터 오일러로 지정한다.**

## 2. 미러는 반드시 좌우를 뒤집어야 한다

뒤를 보는 카메라를 그대로 그리면 "뒤로 돌아앉은 사람의 시야"가 된다.
실제 거울은 그것의 좌우 반전이다. 뒤집지 않으면 **오른쪽 뒤차가 미러 왼쪽에
보인다** — 여기서 익힌 감각이 실차에서 정반대가 되는, 이 프로젝트에서 가장
치명적인 오류다.

카메라에 음수 스케일(`camera.scale.x = -1`)을 주는 방법은 쓸 수 없다.
면의 앞뒤(winding)가 뒤집혀 모델이 안팎으로 뒤집혀 보인다.

**대응** — 렌더 타깃에 정상으로 그린 뒤, 화면에 합성하는 사각형의 `scale.x` 를
음수로 두어 UV 를 뒤집는다. 단순한 사각형에 basic 재질이라 winding 문제가 없다.

검증은 눈으로 했다. 차 뒤 좌우에 초록(왼쪽)·자홍(오른쪽) 표식을 세우고
룸미러에서 초록이 왼쪽에 오는지 확인했다.

## 3. 미러 시야각은 실제 거울 크기에서 계산한다

평면 거울이 보여주는 각도 범위는 **눈에서 본 거울의 각크기와 같다.**
임의로 넓히면 사각지대가 사라져 레슨 자체가 성립하지 않는다.

| 거울 | 근거 | 수평 시야각 |
|---|---|---|
| 룸미러 | 가로 26cm, 눈에서 65cm | 22° |
| 좌 사이드 | 가로 16cm, 눈에서 90cm (법규: 10m 뒤 2.5m 폭) | 20° |
| 우 사이드 | 볼록이라 더 넓다 | 28° |

**남은 한계** — 실제 조수석 미러는 볼록거울이라 상이 작고 멀어 보인다
("사물이 거울에 보이는 것보다 가까이 있음"). 여기서는 평면으로 두고 시야각만
넓게 잡았다. 거리 판단 정확도가 부족하면 왜곡을 넣어야 한다.

## 4. 미러 카메라는 자기 차 실내에 가린다

사이드미러 카메라는 도어 패널 바로 옆에 있다. 그대로 두면 미러에 자기 차
실내만 보인다. 미러 렌더 동안 실내를 숨긴다.

레이어(`layers.set`)로 분리하는 방법을 먼저 시도했지만, 위 1번 버그와 겹쳐
원인 판단을 어렵게 만들었다. 가시성 토글이 더 단순하고 검증하기 쉽다.

## 5. 순환 처리를 NPC 에만 넣고 플레이어에는 빠뜨렸다

도로는 600m 주기로 정확히 반복되게 만들었는데(점선 8m, 지주 4m 배수),
정작 플레이어를 순환시키지 않아 도로 밖으로 나가 지면 아래로 떨어졌다.

증상이 1단계의 낙하 버그와 같아 보였지만 원인이 달랐다. 이번엔 경계벽이
아니라 순환이 빠진 것이었다.

## 6. 정지 상태로 고속도로에 스폰하면 즉시 추돌당한다

NPC 에 회피 로직을 넣지 않은 것은 의도한 설계다. 그런데 플레이어를 정지
상태로 놓으니 시속 80km 로 달려오는 뒤차에 곧바로 들이받혔다.

이건 버그가 아니라 **현실적인 결과**다. 대신 도로 진입 시 주행 속도(80km/h)로
스폰하도록 했다. 실제로도 정지 상태로 고속도로에 진입하지 않는다.

## 7. "미러를 확인했는가" 판정 — 인위적 장치를 넣지 않기로 했다

설계 문서에서는 미러 확대 키를 두고 그 사용 여부로 판정하는 안을 검토했다.
실제로 만들어보니 인위적이고, 미러가 항상 보이는 상태에서는 의미가 약했다.

**대신 미러 없이는 판단할 수 없는 상황을 만들었다.** 차선별 속도를 다르게 두어
(1차선 95~105, 2차선 78~88, 3차선 58~65 km/h) 뒤에서 접근하는 차가 늘 있게 했다.
미러를 안 보면 자연히 위험/충돌 판정이 난다.

채점하는 것은 **지시등**과 **사각지대 확인** 두 가지다. 둘 다 명시적 입력이라
판정이 정직하다. 고개를 돌리는 동안 전방이 보이지 않는 대가까지 재현했다.
