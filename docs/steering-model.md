# 핸들 조향 모델 (핵심 설계)

이 문서는 특정 단계에 속하지 않는다. **모든 단계에 걸쳐 적용되는 이 프로젝트의 중심 구조**다.

## 왜 별도 문서인가

이 게임의 목적이 "실제 운전 감각 학습"이고, 그 감각의 대부분은 핸들 조작에 있다. 그런데 일반적인 게임의 조향 구현 방식으로는 이 게임이 가르치려는 것을 **표현할 수조차 없다.**

## 문제: 일반적인 구현은 핸들을 모델링하지 않는다

보통의 레이싱 게임:

```
키 입력 / 스틱 → 앞바퀴 각도 (-35° ~ +35°) → 물리 엔진
```

여기에는 "핸들"이 없다. 앞바퀴 각도만 있다. 그래서 다음을 표현할 수 없다.

- "핸들을 한 바퀴 반 감았다"
- "이제 반 바퀴 푼다"
- "핸들이 지금 중립에서 얼마나 벗어나 있는가"

주차와 좁은 램프 조작(3~4단계)에서 가르치려는 것이 바로 이것이다.

## 해결: 2단 구조

```
[입력]
   ↓
핸들 각도  steeringWheelAngle   -450° ~ +450°  (락투락 2.5바퀴)
   ↓  ÷ 조향비 (steeringRatio)
앞바퀴 각도 roadWheelAngle      -35°  ~ +35°
   ↓
Rapier: setWheelSteering(0, angle), setWheelSteering(1, angle)
```

실제 승용차의 조향비는 **12:1 ~ 18:1** 범위다. 450 ÷ 14 ≈ 32° 로 앞바퀴 최대 조향각과 대략 맞아떨어진다.

### 이 구조가 주는 것

1. **핸들 회전량이 게임의 상태값이 된다** — 화면에 표시할 수 있고, 채점할 수 있고, 레슨의 목표로 삼을 수 있다
2. **입력 장치가 무엇이든 학습 대상이 동일하다** — 키보드로 배운 "한 바퀴 반"이 나중에 실제 휠에서도 같은 의미
3. **3D 핸들을 정확한 각도로 돌릴 수 있다** — 촉각의 시각적 대체가 가능해진다

## 파라미터

전부 튜닝 대상이며 런타임 조절이 가능해야 한다.

| 파라미터 | 초기값 | 설명 |
|---|---|---|
| `maxSteeringWheelAngle` | 450° | 한쪽 끝까지. 락투락 2.5바퀴 |
| `steeringRatio` | 14 : 1 | 핸들 각도 ÷ 이 값 = 앞바퀴 각도 |
| `maxRoadWheelAngle` | 33° | 앞바퀴 물리적 최대 조향각 |
| `handSpeedNormal` | 240 °/s | 일반 주행 시 핸들 회전 속도 |
| `handSpeedParking` | 480 °/s | 저속·정차 시 (실제로 주차할 땐 빠르게 감는다) |
| `returnSpeedFactor` | 속도 비례 | 자동 복원 속도 계수 |

## 입력 → 핸들 각도

**핵심 원칙: 핸들은 순간이동하지 않는다.** 목표 각도로 점프시키면 안 되고, 회전 *속도*로 접근시켜야 한다.

```
handSpeed = lerp(handSpeedNormal, handSpeedParking, 저속일수록 1에 가깝게)
steeringWheelAngle 를 목표 방향으로 handSpeed * dt 만큼만 이동
clamp(-maxSteeringWheelAngle, +maxSteeringWheelAngle)
```

### 자동 복원 (self-centering)

실제 차는 캐스터각 때문에 속도가 붙으면 핸들이 저절로 중립으로 돌아온다.

- 복원 속도를 **차속에 비례**시킨다
- **정차 중에는 복원하지 않는다** — 주차 시 핸들을 감아둔 채로 유지해야 하므로 필수
- 사용자가 입력 중일 때는 복원을 적용하지 않는다

### 속도 감응 처리 — 일반 게임과 다르게 간다

일반 게임은 고속에서 **최대 조향각 자체를 좁힌다**(35° → 8°). 이 게임에서 그렇게 하면 "핸들을 끝까지 감았는데 안 꺾인다"는 거짓 감각을 학습시키게 된다.

대신 **조향비를 속도에 따라 키운다.** 핸들은 항상 450°까지 돌아가되, 고속에서는 같은 핸들 각도가 더 작은 앞바퀴 각도로 변환된다. 실제 가변 조향비(VGR) 차량과 같은 방식이고, 물리적으로도 정직하다.

| 속도 | 조향비 | 핸들 450°일 때 앞바퀴 |
|---|---|---|
| 0 ~ 20 km/h | 14 : 1 | 32° |
| 60 km/h | 24 : 1 | 19° |
| 100 km/h 이상 | 40 : 1 | 11° |

### 입력 커브

- **키보드/스틱**: 중앙 근처를 둔감하게 (`input^1.5`) → 직진 유지와 미세 수정이 쉬워짐
- **마우스/자이로/실제 휠**: **커브를 적용하지 않는다.** 각도 자체가 정보이므로 왜곡하면 감각 학습이 무의미해진다

## 장치별 입력 매핑

| 장치 | 방식 | 특징 |
|---|---|---|
| **키보드** (A/D 또는 ←/→) | 누르고 있는 동안 핸들 각도 누적 | 구조적으로 실제 핸들과 동일(회전 누적). 위치 피드백만 없음 |
| **마우스** (Pointer Lock) | 상대 이동량을 각도로 누적. 예) 30cm → 1바퀴 | 해상도가 높아(1000+ dpi) **미세 조향이 가능**. 자기 복원 없음이 오히려 실제와 같음 |
| **폰 자이로** | 화면을 누른 동안만 "핸들을 잡은" 상태 | 아래 참조 |
| 게임패드 스틱 | 스틱 위치 → 목표 각도 | 엄지 이동 거리가 짧아 정밀도 낮음 |
| (미래) 휠 컨트롤러 | `axes[0]` 직결, 커브 없음 | 캘리브레이션 UI 필요 |

### 폰 자이로 — 그립/릴리즈로 범위 한계를 푼다

폰을 두 손으로 잡고 편하게 돌릴 수 있는 범위는 ±90° 정도로, 실제 핸들 900°의 1/5에 불과하다. 해법:

> **화면을 누르고 있는 동안만 핸들을 잡은 것으로 처리한다.**
>
> 누른 채 돌린다 → 핸들이 돌아간다
> 손을 뗀다 → 핸들 각도가 유지된다
> 폰을 원위치로 되돌리고 다시 누른다 → 이어서 돌린다

마우스를 들어서 다시 놓는 것과 같은 원리인데, **동시에 실제 운전자가 주차할 때 하는 손 바꿔 잡기와 정확히 같은 동작**이다. 범위 한계가 결함이 아니라 현실적인 제약이 된다.

구성: 폰은 자이로 값만 WebSocket으로 전송, 화면은 PC. 미러와 원근이 큰 화면에서 살아난다.

**주의사항**
- iOS는 `DeviceOrientationEvent.requestPermission()`을 사용자 탭 안에서 호출해야 하고 HTTPS 필수
- 중립점 캘리브레이션 필요 (폰을 편한 자세로 들고 탭)
- 저역 통과 필터로 노이즈 제거

## 촉각의 시각적 대체

포스 피드백이 없으므로 "지금 핸들이 얼마나 꺾여 있는가"를 시각으로 전달해야 한다.

- **운전석 시점의 3D 핸들** — 실제 각도대로 회전. 운전석 시점이므로 어차피 화면에 있어야 하는 물체이고, 추가 비용이 거의 없다
- **12시 방향 마커** — 핸들 상단에 표시 하나. 회전량이 직관적으로 읽힌다
- **조향각 수치 표시** — 학습 단계에서는 켜두고, 익숙해지면 끄는 옵션
- **락 도달 피드백** — 끝까지 감겼을 때 소리 + 핸들 정지

실제 운전 교육에서도 초보는 처음엔 핸들을 보면서 배운다. 시각 의존은 학습 초기에는 오히려 자연스럽다.

## 아커만 조향 (3~4단계에서 도입)

회전할 때 안쪽 바퀴와 바깥쪽 바퀴는 회전 반경이 다르므로 조향각도 달라야 한다. 안쪽 바퀴를 더 많이 꺾는다.

1~2단계에서는 좌우 동일 각도로 충분하다. **좁은 곳에서의 저속 선회(3~4단계)에서는 궤적이 눈에 띄게 달라지므로** 그때 도입한다.

## 구현 시 함정

- **모든 보간은 `dt` 기반이어야 한다.** 프레임 기준으로 짜면 120Hz 모니터에서 핸들이 두 배 빨리 돌아간다
- 물리는 고정 스텝(1/60)으로 돌리고, 입력 폴링은 프레임마다 한다
- 핸들 각도는 물리 상태가 아니라 **입력 상태**다. 물리 스텝과 별개로 관리하고, 물리 스텝 직전에 앞바퀴 각도로 변환해 적용한다
