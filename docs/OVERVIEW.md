# 운전 연습 시뮬레이터 — 프로젝트 개요

## 한 줄 정의

경쟁이 없는 웹 기반 운전 게임. 실제 운전에서 필요한 **감각과 절차**를 익히는 것이 목적이다.

## 목적

일반적인 자동차 게임은 다른 차와 경쟁해 1등을 하는 것이 목적이다. 이 프로젝트는 다르다.

**가르치려는 것**

- 차선을 변경할 때 사이드미러 속 뒤차가 어느 정도 크기·위치일 때 들어가도 되는가
- 빼곡한 주차장에서 차를 빼는 절차 — 핸들을 언제 얼마나 감고, 언제 푸는가
- 폭이 좁은 주차장 램프를 긁지 않고 오르내리는 정밀 조작
- 차체의 크기와 회전 반경에 대한 감각

**가르치지 않는 것 (의도적으로 제외)**

- 속도 경쟁, 랩타임, 순위
- 드리프트 등 한계 주행
- 교통 법규 지식 (필기시험 영역)

## 이 게임이 성립하려면 반드시 지켜야 하는 것

### 1. 경쟁 요소를 넣지 않는다

경쟁이 들어오는 순간 사용자는 "빨리 가는 법"을 최적화하기 시작한다. 이 게임의 학습 목표와 정면으로 충돌한다.

### 2. 핸들 각도가 1급 상태값이다

대부분의 운전 게임은 입력을 **앞바퀴 각도**에 바로 연결한다. 그러면 "핸들을 한 바퀴 반 감았다"는 개념이 코드에 존재하지 않는다.

이 프로젝트는 **핸들 각도(±450°)와 앞바퀴 각도(±35°)를 분리하고 조향비로 연결한다.** 이것이 이 게임을 다른 운전 게임과 구분짓는 가장 중요한 구조적 결정이다.

자세한 내용: [핸들 조향 모델](./steering-model.md)

### 3. 그래픽보다 깊이 단서를 우선한다

예쁠 필요는 없다. 그러나 **거리와 형태는 확실히 읽혀야 한다.** 거리 판단이 안 되는 화면에서는 학습이 성립하지 않는다.

우선순위: 바닥 격자 패턴 > 그림자 > 원거리 페이드(fog) > 모서리 강조 > 그 외 모든 것

### 4. 입력 장치를 추상화한다

```
[입력 장치]   키보드 · 마우스 · 폰 자이로 · 게임패드 · (미래) 휠 컨트롤러
     ↓
[조작 상태]   steer · throttle · brake · gear     ← 여기서 감각이 만들어진다
     ↓
[차량 물리]   Rapier DynamicRayCastVehicleController
```

중간층을 정규화된 값으로 고정하면, 장치를 바꿔도 조작감 튜닝 결과가 유지된다.

### 5. 조작 수치는 전부 런타임에 조절 가능해야 한다

이 게임은 "운전하는 느낌"이 전부이고, 그 느낌은 수십 번의 반복 튜닝으로만 나온다. 수치를 바꿀 때마다 코드를 고치고 리로드하면 1단계에서 프로젝트가 멈춘다.

**튜닝 패널과 텔레메트리는 기능이 아니라 인프라다. 1단계에서 만든다.**

## 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 렌더링 | **Three.js (바닐라)** | 프레임 루프와 물리 스텝 사이에 레이어가 없어 반복 튜닝에 유리. 운전 게임 참고 예제가 가장 많음 |
| 물리 | **Rapier 3D (WASM)** | `DynamicRayCastVehicleController` 내장. Bullet의 btRaycastVehicle 계열이라 튜닝 노하우를 그대로 참고 가능 |
| 빌드 | Vite + TypeScript | 프론트엔드 표준 |
| 튜닝 UI | lil-gui (예정) | 런타임 파라미터 조절 |

React Three Fiber도 후보였으나, PoC 단계에서는 추상화 레이어가 튜닝 디버깅을 방해한다고 판단. 게임 밖 UI(레슨 선택, 결과 화면)가 커지면 그때 이전을 검토한다. 물리 엔진은 어느 쪽이든 동일하다.

## 단계 로드맵

각 단계는 독립적으로 "플레이 가능한 상태"로 끝난다. 어디서 멈춰도 결과물이 남는다.

| 단계 | 산출물 | 검증 질문 | 문서 |
|---|---|---|---|
| **0** | Three + Rapier 셋업, 평면 위 박스 차, 운전석 시점 | 조작 루프가 도는가 | [stage-0](./stage-0-setup.md) |
| **1** | 공터 자유 주행, 조작감 튜닝, 튜닝 패널 | **"운전하는 느낌"이 나는가** | [stage-1](./stage-1-open-lot.md) |
| **2** | 직선 도로, 미러, 차선 변경 레슨 | 미러 보고 타이밍을 잡을 수 있는가 | [stage-2](./stage-2-lane-change.md) |
| **3** | 좁은 램프, 긁힘 판정, 저속 재튜닝 | 정밀 조작이 되는가 | [stage-3](./stage-3-narrow-ramp.md) |
| **4** | 빼곡한 주차장에서 차 빼기 | 목표 달성 | [stage-4](./stage-4-parking.md) |

**작업량은 균등하지 않다.** 1단계(조작감 튜닝)가 전체의 절반 이상을 차지할 것으로 예상한다. 2~4단계는 1단계에서 만든 조작감 위에 상황을 얹는 작업이다.

## PoC 범위

**1단계까지.** 공터에서 자유롭게 주행하며 "운전하는 느낌이 나는가"를 판단한다. 여기서 느낌이 안 나오면 2~4단계는 의미가 없으므로, 이 지점에서 계속 진행할지 결정한다.

## 정직한 한계

프로젝트를 시작하기 전에 명확히 해둔다.

### 포스 피드백이 없다

브라우저에서는 휠 컨트롤러의 FFB(노면 반력, 셀프 얼라이닝 토크)에 접근할 수 없다. Gamepad Haptics는 진동뿐이다. WebHID로 기기 프로토콜을 직접 다루는 방법이 있으나 기기별 역공학이 필요한 별도 프로젝트급 작업이다.

실제 운전에서 "핸들이 무거워지는 느낌", "저절로 돌아오려는 힘"은 조향량을 알려주는 큰 단서인데, 이것을 촉각으로 전달할 수 없다.

**대체 수단:** 운전석 시점의 3D 핸들(현재 각도를 시각화), 조향각 수치 표시, 타이어 슬립음, 화면 흔들림.

### 락(끝까지 감김) 감각이 없다

핸들이 끝까지 돌아갔을 때의 저항을 만들 수 없다. 소리와 화면 핸들 정지로 대체한다.

### 그래서 목표를 이렇게 잡는다

이 게임은 **실차 연습을 대체하지 않는다.** "판단과 절차를 익히는 도구"다.

- 차선 변경 타이밍 판단 → 충분히 가르칠 수 있다
- 주차 시 핸들을 감고 푸는 순서와 양 → 충분히 가르칠 수 있다
- 실제 차량의 무게감, 노면 감각 → 가르칠 수 없다

이 구분을 사용자에게도 명시하는 것이 정직하다.

## 알려진 기술적 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| 조작감 튜닝에 시간이 몰림 | 전체 일정의 50%+ | 튜닝 패널·텔레메트리를 1단계에 먼저 구축 |
| 저속 풀조향에서 레이캐스트 차량이 떨림 | 3~4단계 진입 불가 | 3단계에서 저속 전용 파라미터 세트 분리 |
| 미러 렌더링 비용 (씬을 3~4회 그림) | 프레임레이트 | PC 한정 + 미러 해상도/렌더 거리 축소 |
| 좁은 레벨 설계의 노가다 | 3~4단계 소요 시간 | 레벨을 데이터(JSON)로 분리해 반복 조정 비용 절감 |
